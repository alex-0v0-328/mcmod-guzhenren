# GitHub Commit and Push Skill

When Alex asks to commit, push, or commit and push ("走提交流程"), go straight into this flow. Every step runs on its own, with no step-by-step asks, no commit-title question and no separate push confirmation: the agent picks the titles and runs `commit_push.py`, which commits, gates and pushes. Commits carry Alex's identity alone: no AI agent (Claude, Codex, opencode) is ever added as a contributor — no `Co-Authored-By` or other AI trailer, no generated-with line, no AI author or committer, no `git config` change — and an attribution line the harness supplies is dropped. Each repository ships its main checkout to `main` on origin; no PR unless Alex asks for one.

Paths below are relative to Guzhenren's root. The flow serves all three repositories through one tool: Guzhenren, where every tool lives, Gu World (`../mcmod-guworld`) and the wiki (`../mcmod-wiki-gzr`). One plan may hold commits for all three; a commit names its repository with `"project"` (`guzhenren`, `guworld` or `wiki`; default `guzhenren`, or what `--project` names). For Gu World every `local_checks.py` call adds `--project guworld`.

## Flow

1. **Check the changes.** Start from `git status` and attribute every changed file: the agent's own work, Alex's live IDEA edits (his ask means he is done editing), or another session's WIP, which stays out unless Alex says otherwise. `commit_push.py` itself verifies the planned tree with the tool tests, `build`, `data` and `gametest`, so before shipping run only what it lacks: `python -B tools/local_checks.py server` for a change to mod code or data, plus `client multiplayer` when client code, a renderer or a resource changed.
2. **Prepare the commits.** Group the changes by independent purpose; each group carries its own tests, providers and generated resources, and every commit includes its datagen output. A commit takes whole files (`files`; a folder written with a trailing `/` takes everything under it, deletions included), or part of a file whose other hunks belong to another group or another session: `patches` lists `git diff` output cut down to this commit's hunks, `contents` maps a repository path to a file holding exactly what should be committed. Never ship a whole shared file into the wrong group, and never commit by hand to get around it. A folder entry ships every changed path under it, whoever edited it; preflight spells out an entry that takes more than 50.
3. **Pick commit messages.** A title Alex named for a group is used as given. Otherwise, the agent writes the one title it would recommend and goes on — no question, no option list; the report shows every title used. Messages follow Conventional Commits: a title `<type>[(scope)][!]: <description>`, then an optional body and optional footers, each after a blank line. Types: `feat` new content or behavior, `fix` a bug fix, `refactor` a code change that alters no behavior, `perf` a speedup, `test` tests only, `docs` documentation only, `style` formatting only, `build` the build scripts, Gradle or dependencies, `ci` the GitHub workflows, `chore` anything else (a release is `chore(release): <version>`). The scope is optional and lowercase (a package or area: `aperture`, `refinement`, `worldgen`). A breaking change (a save, id or network-protocol break) adds `!` after the type or scope and a `BREAKING CHANGE: <what breaks>` footer. The description is lowercase imperative English without a trailing period. The body, when the title alone cannot carry it, explains why. A message holds only what the commit changes: no process, batch or decision numbers, check or CI results, dates or session notes, and no footer but `BREAKING CHANGE`. `mod_version` bumps are Alex's call per release.
4. **Commit and push.** Write the plan into this task's own folder, `../../Temps/guzhenren/<task folder>/plan.json` (never a shared file name: sessions ship side by side) — `{"commits": [{"project": "...", "title": "...", "body": "...", "files": [...], "patches": [...], "contents": {...}}]}` in commit order (`project`, `body`, `patches`, `contents` optional), repository paths relative to that repository's root, patch and content sources relative to the plan's folder — and run `python -B tools/commit_push.py <plan>` right after the titles are set, without a separate `--dry-run`. In order, it runs: preflight (`main` checked out, remote not ahead, every plan path changed, every compile jar of `run/mods` downloaded in CI), which derives each repository's tree in a scratch index and leaves the checkout and its index alone; verify, in one of two parallel slots and off the Gradle lock, on an export of exactly that tree, with the stages the change calls for — nothing for README and editor files, the tool tests for `tools/`, `.claude/`, `AGENTS.md`, what GitHub runs (build, runData drift) plus JUnit with the wiki gate and the GameTests for everything else (≈1–2 min), the link check for the wiki (`--full` forces every stage); landing, under one short lock: each tree must still be the verified one, else the run verifies again (another session landed first), then the commits are built beside the branch, the contributor gate reads them, each branch moves in one step and is pushed, Gu World, Guzhenren, wiki in that order; a wait for each pushed SHA's Actions run with no lock held (15-minute default, `--poll-timeout`). Alex's concurrent edits are never reverted and nothing is ever half committed.
5. **Contributor gate.** Before any branch moves, `commit_push.py` reads every commit the push would add, `origin/main..<new tip>` (when origin has no `main` yet, every commit no origin branch holds). It refuses when an author or committer differs from the `git config` identity or looks like an AI, or when a message carries a `Co-Authored-By` or generated-with line. Nothing is committed then: fix the plan and re-run. When the offender is a commit already made by hand, fix it (reword, or reset the author on the unpushed commits only) and run `commit_push.py --push-only`, which verifies the unpushed commits like any plan, re-runs the gate, pushes and waits for CI. When the configured identity itself is the problem, stop and tell Alex — the agent never changes `git config`. Nothing is pushed until the gate passes.
6. **Report.** Read the `commit_push-<pid>.log` the run printed (under `../../Temps/guzhenren/logs/`, or `../../Temps/guworld/logs/` with `--project guworld`). Report each commit's SHA, title, push state and the real CI state as observed, quoting the failing step's log lines for a red run. Delete the plan with the log, and delete the shipped work's to-do from wiki《维护说明#待办与计划》.

## Both repositories

- Gu World's check runs `build`, its GameTests (its only local tests), then its datagen drift, after building Guzhenren's jar once. Its verification runs `build` and the `data` drift check as its GitHub workflow does (which builds Guzhenren's `main` first), then runs `gametest`. Each mod is verified against the other exported from its committed tree — or, when one plan ships both, from the tree that plan gives it — never against the other's work tree. The contributor rule and the gate apply unchanged.
- A repository or remote with no commit yet ships too: the first push creates the branch and sets the upstream.
- When a change spans both repositories, put both in one plan: the tool ships Gu World first, so Guzhenren's runs and links already find it. The exception is a change to a jar Guzhenren's build script compiles against (its file name in `build.gradle` and both workflows): Gu World's CI builds Guzhenren's pushed branch, so the plan adds `"order": ["guzhenren", "guworld"]`.
- Gu World carries no rules or harness files: Guzhenren's `AGENTS.md`, skills, subagents and configs serve both repositories and ship with Guzhenren.

## Wiki

The wiki (`../mcmod-wiki-gzr`, private `alex-0v0-328/guzhenren-mod-wiki`, `.obsidian/` untracked) ships through the same tool, after the mods it documents: one `"project": "wiki"` commit titled `docs: ...` listing only the pages this task touched (another session's page edits stay out unless Alex says otherwise), in the mods' plan or a plan of its own. Its verification is `doc_conventions.py links` on the exported pages; it has no CI to wait for.

## Push rules

- No force push and no rewrite of pushed history; for pushed work a new commit beats `--amend`. Never `--no-verify`, `--no-gpg-sign` or `-c commit.gpgsign=false` — a failing hook is fixed at its cause.
- A preflight, verification or gate failure stops before anything is committed; fix the cause and re-run. A failed verification keeps its export under `../../Temps/guzhenren/ship/failed-<pid>/`. When the remote moved ahead, pull (keep both sides' work) and re-run.
- `python -B tools/commit_push.py --ci <sha>` re-checks a commit's CI by hand (with `--project guworld` for Gu World).
- When one plan ships several repositories and a later push fails, the earlier ones are already pushed: drop their commits from the plan before re-running.
- A push refused with `Invalid username or token` means the stored GitHub credential is wrong (Git Credential Manager answers from the Windows Credential Manager): the commits stay local, Alex fixes the credential, then `commit_push.py --push-only` ships them.

## CI red

When Alex brings a GitHub Actions failure, the loop locate → fix → this flow → green runs without waiting for an explicit commit request — a red CI left unpushed counts as unfixed. Titles follow step 3.

## Traps

- Commit status and Actions check runs are separate queries — an empty status is not "CI green", and neither are "queued", "in progress" or "no run found".
- A hard dependency referenced straight from `run/mods` needs its CI download step, otherwise CI goes red while local stays green.

## After

When a change moved folders or packages or touched a build script, the agent confirms IDEA's Gradle reload through the JetBrains MCP where the session has it, and asks Alex for the reload button only when it did not happen (`AGENTS › Checks and shipping`). Before a change that rewrites many files (a move, a rename), ship any pending WIP first and ask Alex to pause IDEA edits until it lands.
