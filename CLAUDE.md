Collaboration rules live in the alex-constitution skill, Alex's rules for every project, which a SessionStart hook injects into every Claude Code session (CLAUDE › Tools and context) and which outranks this file; the task skills beside it in `.claude/skills/` own their workflows (`activate-dashboard`, `commit-push`, `session-close`). Alex's chat instructions beat both. Apart from alex-constitution and i-have-adhd, no parent-workspace or global rules file outranks or extends them. Everything else loads on demand, never whole: domain facts from [reference/](reference/README.md), one file per topic, workflows from `rules/` through the Workflow router, the wiki by affected page.

- Numbers live in code: Gu specs in `ModItems.GuSpec`, characters in their enums and services. The dev wiki explains design and reasoning; the player wiki is a version snapshot. One primary number location per audience; everything else references it.
- Scope is mortals, rank 1..5 (一转..五转); nothing shaped for stage 3 and later (ascension 仙, immortal Gu, rank 6..9) gets built or counted as missing. The one exception is the Treasure Yellow Heaven dimension (appearance-only first version).
- Two mods make the game. **Gu World**, the sibling project `../guworld` with its own Git repo and rules file (mod id `guworld`, package `net.alex.guzhenrenworld`), owns every dimension and its terrain, overworld terrain both new and vanilla-modified, biomes, and naturally generated unique structures such as the spirit spring (元泉: its worldgen lives there, its block, fluid, item and rendering here). **guzhenren** owns everything else, including travel into those dimensions, their guards and the settlements (山寨, 城镇, 村落, the vanilla village rework). They meet only at run time: Gu World requires guzhenren and loads after it, neither compiles against the other, and each names the other's content by id alone — guzhenren a dimension by its level key (`ModDimensions`), Gu World the spring block (`GuzhenrenBlocks`) — so a rename touches both projects in one task. This repository is where both run together: `build.gradle` puts Gu World's built jar on the run classpath (`-PguWorldDir`, default `../guworld`). The full game needs both mods plus the pack; the split exists for design isolation. Ownership and what is not yet scheduled: wiki《待定设计》.
- Never add Claude as a contributor, in this or any sibling repository: no `Co-Authored-By` or generated-with line and no Claude identity in any commit, an attribution line the harness supplies included. `commit_push.py`'s contributor gate enforces it locally; a cloud session, which has no `tools/`, follows it by hand.
- Think like a Minecraft modder and a modpack player: gameplay flow, compatibility, maintenance cost. Review against Java types, state invariants, server authority and lifecycle.
- Hardware budget is a standing design constraint: default to restrained block, entity and particle scales, and state magnitude estimates (how many blocks, how many seconds) in reports so Alex can judge by feel (explosion radius 320→112).

## Tools and context

If IDEA is closed, read the disk and the pinned dependency sources. An index never overrides the disk.
- **Docs.** Context7 is an optional lookup; accept only NeoForge 1.21.1 / GeckoLib 4 results, otherwise use the pinned jars and sources. Vanilla and NeoForge runtime behavior comes from the decompiled sources (reference《环境、构建与测试》).
- **Tool economy.** Prefer dedicated read, search and edit tools over shell equivalents; run independent calls in parallel; keep queries short and paths scoped, and don't chain several equivalent indexes for the same answer; cite code as `path:line`.
- **Onboarding.** A new MCP server or plugin counts only after four steps — installed, config valid, callable in session, actually effective — and none is added just for tool count. Credentials stay in the user environment; config files hold variable names only.

The repos are `alex-0v0-328/mcmod-guzhenren`, `mcmod-guworld`, `mcmod-camera-shift` and the public `mcmod-burst-flight`; each local `origin` uses these names.

## Checks and shipping

Two one-command tools replace hand-run Gradle chains and the manual commit ritual. They run on Windows Python, which both runtimes call directly, and each writes one log, `C:\workspace\Dev\Projects\_Temp\<project>\logs\check.log` or `commit_push.log`, which its next run overwrites. Read the log, report from it, then delete it. While one tool drives Gradle, the other refuses to start (`gradle.lock`), so parallel sessions never collide.

`python tools/check.py` runs every stage in this order. Naming stages runs only those, `--headless` skips the client, and `--list` describes each stage. Times are warm-cache; a cold build adds 2–3 minutes.

| Stage      | What a pass proves                                                                                                                                                              | Warm time |
|------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------|
| `build`    | Compile and jar pass, plus L1 `pureTest` and L2 `test` JUnit; the wiki gate `-PwikiDir` is on whenever the wiki exists                                                          | 0–2 min   |
| `gametest` | Every L3 `@GameTest` passes on the dedicated GameTestServer                                                                                                                     | ≈0.5 min  |
| `data`     | `runData` reproduces `src/generated` byte for byte (the CI drift check); a rewrite fails and lists the files to review                                                          | ≈0.3 min  |
| `server`   | `runServer` in a throwaway Temp world without the pack mirror: boot, summon every mod entity, place every mod feature, load every Gu World dimension, tick 20 s, stop over RCON | ≈0.7 min  |
| `client`   | `runClient` with the `run/` pack reaches the title screen and stays alive 20 s, then closes; opens a window, and skips while a game from this checkout runs                     | ≈0.8 min  |

- During iteration, run the stages the change touches; the `commit-push` skill runs the full check before shipping. Visual and feel acceptance in `runClient` stays Alex's; every Gradle command and IDE sync check is the agent's. After a build-script change, confirm IDEA's reload through the JetBrains MCP (`get_project_modules`, `get_run_configurations`); the MCP has no sync action, so ask Alex for IDEA's reload button only when those still show the old layout.
- The game stages (`gametest`, `server`, `client`) first run `clean assemble` in `../guworld` and load its jar; without that project they fail. Every Gu World stage likewise first runs `clean assemble` here.
- `python tools/commit_push.py` is the commit tool behind the `commit-push` skill, which owns the flow and describes every stage.
- Both tools also drive the sibling repositories (registry `gzr_env.PROJECTS`) with `--project guworld`, `camerashift` or `burstflight`. Check runs Gu World's `build` (with its local JUnit), `gametest` and `data`; Camera Shift's `build`; Burst Flight's `build` and `gametest`. The commit-push mirror first runs `build` as the sibling's CI does, then the same check stages with `src/test` copied in. A repository or remote with no commit yet ships too.
- This IDEA window links Gu World, Camera Shift and Burst Flight as Gradle projects. Their run configurations carry a prefix and a folder (`Gu World Client`, `Camera Shift Client`, `Burst Flight Client`, via `ideName` / `ideFolderName`), so GZR's plain `Client`, `Data`, `Server` and `GameTestServer` stay its own; a new linked project needs the same.
- The test suites are local-only, here and in the siblings: `src/test/` is gitignored, GitHub Actions only compiles, packages and checks datagen drift, and the commit-push mirror is where tests guard a push. They have no remote copy and no version history.
- The siblings follow this repository wherever GitHub sees them: the same `.gitignore` sections, `.gitattributes`, `.editorconfig`, `LICENSE.txt`, the README set (`README.md` in Simplified Chinese, Alex's source, with `README.zh-TW.md` and `README.en.md` translated from it), a tracked `CLAUDE.md` and the `.claude/` cloud files, and the code conventions of Language and style, which each sibling's `CLAUDE.md` condenses for cloud sessions.

## Language and style

- Chat in Chinese (zh-CN); think in English, the model's strongest language — only the reply is Chinese. Code, comments and commit messages in American English. `CLAUDE.md`, `rules/` and `.claude/skills/` are written in English, `reference/` in Chinese.
- Terms come from the language provider, `en_us.json` and the wiki《原著词汇 与命名》 — never invent bilingual pairs (known trap pairs in reference《写作与命名》).
- New code matches its neighbors' comment density, naming and idiom; formatting follows `.editorconfig`; comments explain non-obvious reasons only. No bulk reformat, no project-wide IDEA "cleanup code". Substantive conventions (the five naming rules with the one-way package dependencies, `@NotNull`/`@Nullable`, import ordering, Javadoc FQN rules) live in reference《写作与命名》.
- Cross-references name the heading — `CLAUDE › Boundaries`, reference《心跳顺序》, `[[待定设计#…]]` in the wiki — never a section sign or a section number, and headings carry no number prefixes.
- Markdown tables stay aligned: a padded table pads every column to its widest cell in display width (CJK counts 2) and its separator to that width plus two dashes, tight `|---|` in rules files and READMEs, spaced `| --- |` in the wiki; compact `|---|` tables stay compact. Any added or edited row re-pads the whole table: after touching a table, `python tools/md_tables.py <file>` must report nothing (`--fix` re-pads).
